
\subsection{Tool Support and Evaluation Mapping}\label{sec:method:tools}

{\tech} is implemented as a modular Python package.  The collector, scanner, RQ2 tool analyzer, RQ3 fuzzing driver, and RQ4 source-reproduction driver are separate components with CSV outputs at each stage.  This design keeps the workflow simple for full-study runs while preserving intermediate artifacts for auditing and reruns.  It also keeps measurement responsibilities separate: the scanner records what exists in distributions, whereas RQ-specific analyzers decide which observations are in scope for a particular research question.

The version-management logic is central to the design.  The scanner exports a CPython-version summary, and later phases use that list to prepare matching interpreters and per-version environments.  RQ2 uses the scanner's interpreter mapping to select modern CPython bytecode entries with prepared runtimes and excludes older or unsupported entries from tool-failure counts.  This avoids the misleading failure mode where a bytecode artifact is judged unanalyzable only because the host machine lacks the correct CPython version.

The fuzzing component is also version-aware.  It extracts CPython unittest seeds, compiles them using the same interpreter version that will be fuzzed, and stores one seed corpus per CPython tag.  The source-reproduction component consumes RQ3 findings and reports decompiler, compilation, and reproduction outcomes separately so that evaluation claims remain tied to observable tool behavior.

\subsection{Ethical and Safety Considerations}\label{sec:method:ethics}

The study does not execute unknown packages on the host system.  Package installation, import probing, decompilation, and runtime tests are performed in isolated environments with network access disabled unless a dataset-construction step explicitly requires downloading public artifacts.  Malicious or suspicious samples are handled as research data, and bytecode-only crashes are reported as robustness findings rather than automatically being labeled exploitable vulnerabilities.  When a finding indicates a potential interpreter security issue, it should be disclosed through the appropriate upstream security process before public release.
