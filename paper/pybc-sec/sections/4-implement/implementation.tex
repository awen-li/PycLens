\section{Methodology}\label{sec:method}

\subsection{Overview}\label{sec:method:overview}

{\tech} is an empirical pipeline for studying Python bytecode visibility and robustness.  The pipeline has five stages.  The dataset builder collects packages and application artifacts.  The extractor inventories source files, \texttt{.pyc} files, \texttt{\_\_pycache\_\_} directories, marshalled code objects, bytecode-bearing archives, and dynamic loading patterns.  The correspondence analyzer compiles available source under the expected interpreter version and compares it with observed bytecode.  The recovery analyzer applies decompilation and recompilation workflows, then compares recovered artifacts against the original bytecode.  Finally, the robustness analyzer runs real and generated bytecode inputs across CPython versions and applies source-reachability checks to abnormal outcomes.

\subsection{Data Collection}\label{sec:method:data}

We construct datasets from multiple sources to reduce bias.  The first dataset contains popular PyPI packages selected by download counts or dependency centrality.  The second contains randomly sampled PyPI packages across popularity and age.  The third contains packages reported as malicious or suspicious by public advisories, security vendors, or package-index takedowns.  The fourth contains Python application bundles and release artifacts such as wheels, archives, container layers, and PyInstaller-style outputs.  The fifth contains runtime-testing inputs derived from CPython tests, real bytecode artifacts, and generated bytecode variants.

For each package or artifact, {\tech} records the package name and version, distribution type, file inventory, source and bytecode paths, bytecode magic number, inferred Python version, hashes, and import or load behavior when such behavior can be determined statically.  Multiple dataset classes reduce dependence on one distribution channel, while artifact hashes and explicit version metadata make every extracted input reproducible.  Ambiguous cases are reported separately, including unknown bytecode versions, unparsable artifacts, encrypted or packed payloads, and dynamic loaders whose target cannot be resolved.

\subsection{Phase 1: Bytecode Artifact Extraction}\label{sec:method:extract}

The extractor parses \texttt{.pyc} headers, recovers marshalled code objects, disassembles instruction streams, recursively visits nested code objects, and records metadata such as constants, names, variables, flags, exception tables, closures, and line-position information.  It also scans source for dynamic loading APIs including \texttt{marshal}, \texttt{importlib}, custom loaders, and direct calls to \texttt{exec} over recovered code objects.

This phase supports RQ1 and RQ2.  RQ1 depends on accurately counting bytecode-bearing artifacts across datasets.  RQ2 depends on extracting the bytecode object that should be compared with candidate source rather than relying only on filenames.

\subsection{Phase 2: Source Correspondence Analysis}\label{sec:method:source}

For each bytecode artifact, {\tech} searches for corresponding source using path conventions, module names, archive metadata, and package layout.  When source is available, the pipeline compiles it under the expected Python version and compares the resulting code object against the observed bytecode.  The comparison includes opcode sequences, constants, names, locals, nested code objects, control-flow shape, exception tables, flags, and line metadata.

We classify artifacts as source-present and matching, source-present but mismatched, source-missing, dynamically generated or loaded, bundled or packed, or unknown.  Python bytecode changes across versions, so interpreter mismatch is treated as an explicit outcome rather than silently comparing incompatible artifacts.  Exact bytecode equality is used when available; relaxed structural comparison is used only to explain differences such as line metadata or position tables.

\subsection{Phase 3: Recovery and Tooling Analysis}\label{sec:method:recovery}

{\tech} evaluates source recovery by running selected decompilers on bytecode artifacts, checking whether recovered source is syntactically valid, recompiling recovered source, and comparing the resulting bytecode and behavior with the original when execution is safe and deterministic.  Failure categories include unsupported Python versions, unsupported opcodes, unusual control flow, exception-table mismatch, malformed code-object metadata, dynamic loading, and cases where decompilation succeeds but recompilation changes behavior.

The justification for this phase is that source visibility cannot be answered by file presence alone.  A \texttt{.py} file may exist but compile to different bytecode, while a decompiler may produce source that parses but no longer preserves the original behavior.  A decompiler failure indicates a recovery limitation, not proof that source never existed.

\subsection{Phase 4: Runtime Robustness and Source Reachability}\label{sec:method:runtime}

To study runtime robustness, {\tech} executes bytecode-level inputs under multiple CPython versions, including CPython 3.10, 3.11, and 3.12, and optionally debug or sanitizer builds.  Inputs include real bytecode artifacts, structured bytecode variants, and a raw byte-mutation baseline.  Outcomes are classified as load failure, Python-level exception, normal termination, timeout, assertion failure, abort, segmentation fault, or sanitizer finding.  We deduplicate abnormal outcomes using signal type, top stack frame, failure location, assertion message, crash-address bucket, input hash, and code-object feature signatures.

For each abnormal outcome, {\tech} checks source reachability.  It attempts to decompile the bytecode, recompile the recovered source, re-execute under the same runtime, and compare the failure signature.  Outcomes are classified as source-reproducible, bytecode-only under current tools, decompilation failed, recompilation failed, behavior mismatch, or inconclusive.  This step separates bytecode-level robustness findings from ordinary source-level vulnerabilities and prevents overclaiming from malformed bytecode inputs.

\subsection{Tool Support and Evaluation Mapping}\label{sec:method:tools}

{\tech} is implemented as a modular analysis pipeline.  The artifact inventory component walks extracted package trees and archive contents, normalizes paths, identifies Python source and bytecode files, and records hashes for reproducibility.  The bytecode parser reads \texttt{.pyc} headers, validates magic numbers, unmarshals code objects in an isolated interpreter process, and emits a normalized representation of code-object metadata and disassembled instructions.  Nested code objects are analyzed recursively so that functions, lambdas, comprehensions, class bodies, and embedded code objects are not missed.

The source correspondence component compiles candidate source files with the interpreter version inferred from bytecode metadata whenever possible.  Because Python bytecode is version-sensitive, {\tech} treats interpreter mismatch as an explicit outcome rather than silently comparing artifacts across incompatible versions.  The comparison engine supports exact bytecode comparison and relaxed structural comparison over opcodes, constants, names, local variables, nested-code shape, control-flow edges, and exception-table layout.

The recovery component invokes decompilers as external tools and records both tool-level failures and downstream validation failures.  Recovered source is parsed, compiled, and compared against the original code object.  The runtime component executes inputs inside sandboxed workers with timeouts, resource limits, and per-version interpreter isolation.  Debug and sanitizer builds can be used to distinguish clean Python exceptions from native-level assertion failures, aborts, and memory-safety findings.

\subsection{Ethical and Safety Considerations}\label{sec:method:ethics}

The study does not execute unknown packages on the host system.  Package installation, import probing, decompilation, and runtime tests are performed in isolated environments with network access disabled unless a dataset-construction step explicitly requires downloading public artifacts.  Malicious or suspicious samples are handled as research data, and bytecode-only crashes are reported as robustness findings rather than automatically being labeled exploitable vulnerabilities.  When a finding indicates a potential interpreter security issue, it should be disclosed through the appropriate upstream security process before public release.
