\section{Methodology}\label{sec:method}

\subsection{Overview}\label{sec:method:overview}

This study treats Python bytecode as a distribution artifact, an analysis target, and an interpreter input.  As shown in Figure~\ref{fig:pipeline-overview}, the study proceeds from ecosystem measurement to tool analysis, runtime robustness testing, and source-reproduction checking.  RQ1 measures bytecode exposure and source transparency in PyPI distributions; RQ2 evaluates the practical analyzability of the observed modern CPython bytecode subset; RQ3 tests CPython robustness under mutated bytecode inputs; and RQ4 checks whether bytecode-level findings can be reproduced from ordinary source using selected tools.
%
The pipeline has four stages aligned with these questions.  First, the data collector downloads Python package artifacts from PyPI and the scanner inventories source files, \texttt{.pyc} files, pycache directories, bytecode versions, source-less bytecode candidates, and dynamic loading patterns.  Second, the tool-analysis stage evaluates whether selected bytecode tools can load, disassemble, and decompile the modern CPython bytecode subset for which version-matched interpreters are prepared.  Third, the CPython fuzzing stage extracts unittest-derived seeds, compiles them into version-matched \texttt{.pyc} files, and fuzzes CPython bytecode processing with honggfuzz.  Fourth, the source-reproduction stage checks whether bytecode-level findings can be reproduced from ordinary source using selected recovery tools.

The remainder of this section follows the structure in Figure~\ref{fig:pipeline-overview}: data collection defines the study population, Phase~1 measures bytecode exposure, Phase~2 analyzes tool support, Phase~3 evaluates CPython bytecode processing, and Phase~4 bounds source-level interpretation of bytecode findings.

\subsection{Data Collection}\label{sec:method:data}

The data-collection component defines the study population for prevalence measurement and the package-derived inputs for later analysis.  We use PyPI because prior empirical and security studies treat it as the central Python package ecosystem for studying package vulnerabilities, dependency risk, and malicious-package detection~\cite{duan2021measuring,alfadel2023empirical,gao2025malguard}.  This is sufficient for our goal: RQ1 asks how bytecode appears in real-world Python distributions, and PyPI provides the public distribution artifacts consumed by package installers and package-security workflows.  PyPI also exposes distribution files through documented index and metadata APIs, which makes the population reproducible~\cite{pypi-index-api,pypi-json-api}.  The boundary is therefore wheels and source distributions, the standard package distribution formats described by Python packaging documentation~\cite{python-packaging-flow,python-package-formats}.  Installed environments, containers, application bundles, and repository snapshots are downstream or development contexts with different denominators, so we keep them outside the prevalence population.

Table~\ref{tab:data-collection-design} summarizes the collection choices that define the dataset denominator.

The collector enumerates package names from the PyPI simple index, queries PyPI's JSON metadata, and selects artifacts from each package's latest release.  For each selected release, it keeps at most one wheel and one source distribution uploaded within the five-year study window.  If the latest release has no selected wheel or source distribution within the window, the package contributes no artifact to the collected dataset.  Source distributions may appear as \texttt{.tar.gz}, \texttt{.zip}, or related archive formats; the scanner records the concrete artifact type.
%
The collection policy shapes the denominator.  Because the dataset is package-balanced rather than upload-balanced, projects with many platform-specific wheels do not dominate the measurement.  We therefore analyze wheels and source distributions as separate strata and report the combined total only as a descriptive summary.
%
For each downloaded artifact, the collector records the package name, version, distribution type, local path, hash, and collection status.  Downloads are parallelized, resumable, and stored under a deterministic layout keyed by source, package, version, and filename.  The scanner then records the source and bytecode inventory, bytecode magic number, inferred filename tag, source-less bytecode candidates, and static dynamic-loading indicators.  Collector and scanner outputs are CSV files so dataset construction can be audited and rerun.  Ambiguous cases remain in the raw scan results rather than being normalized away.

\subsection{Phase 1: Bytecode Exposure and Transparency}\label{sec:method:extract}

The first phase turns collected artifacts into bytecode-exposure and transparency measurements.  It is a static archive-inspection phase: the scanner opens wheels, source distributions, zip archives, tar archives, individual files, and extracted directories without installing or executing package code.  Table~\ref{tab:phase1-scan-fields} summarizes the fields recorded by this scan.

  \caption{Phase~1 scan fields and purpose.}
  \label{tab:phase1-scan-fields}
  \begin{tabular}{p{0.30\linewidth}p{0.52\linewidth}}
    \toprule
    Field & Purpose \\
    \midrule
    Artifact type & Separate wheels, source distributions, and other archives. \\
    Source files & Measure whether bytecode is accompanied by visible Python source. \\

    Source-less candidates & Approximate bytecode that lacks a plausible source counterpart in the same artifact. \\

These fields separate prevalence from source visibility.  Prevalence is measured at both artifact level and file level because one artifact with many cached files differs from many artifacts each containing one bytecode file.  Source visibility is measured by whether a \texttt{.pyc} file has a plausible corresponding source file under package layout and pycache naming conventions.  This is a conservative artifact-local check: it does not claim semantic equivalence, and it does not rule out source existing elsewhere.
%
The scanner preserves ambiguous observations in the raw results.  Unknown bytecode versions, noncanonical filename tags, source-less candidates, and dynamic-loading indicators remain visible in the scan inventory; later phases decide which observations are suitable for version-matched analysis.  Dynamic-loading indicators are static flags for APIs that may load or construct code objects; they do not prove that a bytecode payload is executed or identify the runtime target.  This keeps the prevalence measurement descriptive while preventing later tool failures from being mixed with raw ecosystem inventory.

\subsection{Phase 2: Practical Analyzability}\label{sec:method:source}

The second phase measures the practical boundary of bytecode analysis.  The unit is a \texttt{.pyc} file, not a package: for each bytecode-containing artifact, the analyzer extracts every \texttt{.pyc} entry, resolves its CPython tag, and tests whether selected tools can load, disassemble, or decompile it.  The outcome is the highest level reached: not loadable, loadable only, disassemblable, partially decompilable, or fully decompilable.

The phase is version-aware by design.  Python bytecode is an implementation detail that can change across CPython releases, and the standard disassembler documents this version sensitivity~\cite{python-dis}.  Therefore, a file is included in tool analysis only when the scan identifies a supported modern CPython tag and a matching interpreter is prepared.  In the current scope, this means CPython~3.8 and later; CPython~3.7 and earlier, PyPy tags, unknown tags, and noncanonical tags without an interpreter mapping remain in the raw scan inventory but are excluded from tool-failure counts.  This prevents missing interpreters or unsupported runtimes from being misreported as tool limitations.

The environment-preparation step reads the scanner's version summary, uses the interpreter field to identify canonical CPython runtimes, locates or installs matching interpreters when the host supports it, and prepares per-version virtual environments for tools that depend on bytecode format.  Each analysis step records both status and failure reason, including marshal failure, disassembly failure, unsupported bytecode version, external-tool timeout, nonzero exit, and unavailable decompiler output.  These failure reasons are necessary for interpretation: an environment miss, a loader failure, and a decompiler failure imply different limits.

Tool selection follows five criteria.  \textbf{C1: Availability} requires public, locally runnable tools so the study does not depend on closed services.  \textbf{C2: Python~3 support} keeps the baseline aligned with the modern CPython bytecode observed in the scan.  \textbf{C3: Practical use} favors tools that analysts or developers are likely to encounter through documentation, packaging, or community references.  \textbf{C4: Maintenance or stability} avoids failures caused mainly by obsolete or unreproducible tooling.  \textbf{C5: Method diversity} ensures that the selected set covers loading, disassembly, and decompilation rather than one tool family.  These criteria define a reproducible baseline for this study; they do not rank all Python bytecode tools globally.

\subsection{Phase 3: Interpreter Robustness Under Adversarial Bytecode}\label{sec:method:recovery}

The third phase measures how CPython behaves when bytecode inputs are malformed or adversarial.  The unit is a version-matched \texttt{.pyc} file, and the measured property is robustness of bytecode processing: a malformed input should be rejected by ordinary Python-level failure modes rather than causing an interpreter crash, abort, or uncontrolled hang.
%
Figure~\ref{fig:rq3-fuzzing-workflow} summarizes the version-aware workflow.  The input is the set of modern CPython versions observed in Phase~1 for which a matching interpreter can be prepared; unsupported legacy or non-CPython versions are recorded as out of scope for this phase.  For each version, the phase prepares or reuses the matching interpreter, extracts source seeds from CPython's unittest suite, compiles those seeds into a version-matched \texttt{.pyc} corpus, and feeds the corpus to the \texttt{honggfuzz} backend~\cite{honggfuzz}.  The backend records the execution outcome for each version-specific run.  If the unittest sources are not available locally, the matching CPython source release is obtained and used only for seed extraction.  Compiled seed corpora are stored per CPython version so repeated runs use the same starting population.

The workflow in Figure~\ref{fig:rq3-fuzzing-workflow} separates three concerns that make the measurement interpretable.  First, version matching attributes failures to bytecode processing rather than interpreter mismatch.  Second, unittest-derived seeds start from valid bytecode generated from CPython's own regression tests, which exercise core language and runtime functionality.  This seed quality is important for mutation-based fuzzing: a richer initial corpus reaches more meaningful interpreter behavior before mutation explores malformed states outside the source-compiler path.  Third, the fuzzing harness loads each mutated \texttt{.pyc} file and runs the embedded bytecode with the matching CPython interpreter.  Each run is bounded by timeout and process isolation, and the harness records the resulting behavior as normal execution, Python-level exception, timeout, crash, abort, or other abnormal termination.  We treat crashes, aborts, and persistent timeouts as abnormal findings for RQ3.  Such findings require triage and are not automatically classified as exploitable security vulnerabilities.

\subsection{Phase 4: Source-Reproduction Analysis}\label{sec:method:runtime}

The fourth phase bounds the source-level interpretation of bytecode-level findings from RQ3.  The unit is an abnormal RQ3 finding, such as a crash, abort, or persistent timeout.  For each finding, the phase first reruns the original mutated \texttt{.pyc} under the same version-specific harness to confirm the observed behavior.  It then invokes the selected decompilers from Phase~2, compiles any emitted source with the matching CPython interpreter, and reruns the resulting \texttt{.pyc} under the same harness.  A finding is counted as source-reproduced only when this source-derived bytecode reaches the same behavior class as the original finding.

This design separates three outcomes that otherwise collapse together.  A decompiler may fail to emit source, the emitted source may fail to compile, or the recompiled source may execute but not reproduce the original behavior.  All three cases are reported as \emph{not reproduced by selected tools}, with the failure stage recorded separately.  The claim is therefore tool-bounded: it does not prove that no source-level reproducer exists, only that the selected recovery workflow did not produce one.

This check is needed because bytecode mutation can create code-object states that ordinary Python source may not generate.  Without RQ4, an RQ3 crash could be misread as a source-level interpreter failure.  The decompile--compile--rerun workflow tests whether selected source-recovery tools can bridge that gap for each finding, while keeping negative results limited to the evaluated tools.

\subsection{Tool Support and Evaluation Mapping}\label{sec:method:tools}

{\tech} is implemented as a modular Python package.  The collector, scanner, RQ2 tool analyzer, RQ3 fuzzing driver, and RQ4 source-reproduction driver are separate components with CSV outputs at each stage.  This design keeps the workflow simple for full-study runs while preserving intermediate artifacts for auditing and reruns.  It also keeps measurement responsibilities separate: the scanner records what exists in distributions, whereas RQ-specific analyzers decide which observations are in scope for a particular research question.

The version-management logic is central to the design.  The scanner exports a CPython-version summary, and later phases use that list to prepare matching interpreters and per-version environments.  RQ2 uses the scanner's interpreter mapping to select modern CPython bytecode entries with prepared runtimes and excludes older or unsupported entries from tool-failure counts.  This avoids the misleading failure mode where a bytecode artifact is judged unanalyzable only because the host machine lacks the correct CPython version.

The fuzzing component is also version-aware.  It extracts CPython unittest seeds, compiles them using the same interpreter version that will be fuzzed, and stores one seed corpus per CPython tag.  The source-reproduction component consumes RQ3 findings and reports decompiler, compilation, and reproduction outcomes separately so that evaluation claims remain tied to observable tool behavior.

\subsection{Ethical and Safety Considerations}\label{sec:method:ethics}

The study does not execute unknown packages on the host system.  Package installation, import probing, decompilation, and runtime tests are performed in isolated environments with network access disabled unless a dataset-construction step explicitly requires downloading public artifacts.  Malicious or suspicious samples are handled as research data, and bytecode-only crashes are reported as robustness findings rather than automatically being labeled exploitable vulnerabilities.  When a finding indicates a potential interpreter security issue, it should be disclosed through the appropriate upstream security process before public release.
