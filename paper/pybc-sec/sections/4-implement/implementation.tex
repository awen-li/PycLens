\section{Methodology}\label{sec:method}

\subsection{Overview}\label{sec:method:overview}

{\tech} studies Python bytecode as a distribution artifact, an analysis target, and an interpreter input.  As shown in Figure~\ref{fig:pipeline-overview}, the study proceeds from ecosystem measurement to tool analysis, runtime robustness testing, and source-reproduction checking.  RQ1 measures bytecode exposure and source transparency in PyPI distributions; RQ2 evaluates the practical analyzability of the observed modern CPython bytecode subset; RQ3 tests CPython robustness under mutated bytecode inputs; and RQ4 checks whether bytecode-level findings can be reproduced from ordinary source using selected tools.
%
The pipeline has four stages aligned with these questions.  First, the data collector downloads Python package artifacts from PyPI and the scanner inventories source files, \texttt{.pyc} files, pycache directories, bytecode versions, source-less bytecode candidates, and dynamic loading patterns.  Second, the tool-analysis stage evaluates whether selected bytecode tools can load, disassemble, and decompile the modern CPython bytecode subset for which version-matched interpreters are prepared.  Third, the CPython fuzzing stage extracts unittest-derived seeds, compiles them into version-matched \texttt{.pyc} files, and fuzzes CPython bytecode processing with honggfuzz.  Fourth, the source-reproduction stage checks whether bytecode-level findings can be reproduced from ordinary source using selected recovery tools.

The remainder of this section follows the structure in Figure~\ref{fig:pipeline-overview}: data collection defines the study population, Phase~1 measures bytecode exposure, Phase~2 analyzes tool support, Phase~3 evaluates CPython bytecode processing, and Phase~4 bounds source-level interpretation of bytecode findings.

\subsection{Data Collection}\label{sec:method:data}

The data-collection component defines the study population for prevalence measurement and the package-derived inputs for tool analysis.  Its boundary is PyPI distribution artifacts; it does not collect installed environments, containers, application bundles, or source repositories.  This makes the population public and reproducible, but limits the claims to PyPI distributions rather than all Python deployment formats.

    \bottomrule
  \end{tabular}

{\tech} enumerates package names from the PyPI simple index, queries PyPI's JSON metadata, and selects artifacts from each package's latest release.  For each selected release, it keeps at most one wheel and one source distribution uploaded within the five-year study window.  Table~\ref{tab:data-collection-design} summarizes these choices and their purpose.  Source distributions may appear as \texttt{.tar.gz}, \texttt{.zip}, or related archive formats; the scanner records the concrete artifact type.
%
The collection policy shapes the denominator.  Because the dataset is package-balanced rather than upload-balanced, projects with many platform-specific wheels do not dominate the measurement.  We therefore analyze wheels and source distributions as separate strata and report the combined total only as a descriptive summary.
%
For each downloaded artifact, {\tech} records the package name, version, distribution type, local path, hash, and collection status.  Downloads are parallelized, resumable, and stored under a deterministic layout keyed by source, package, version, and filename.  The scanner then records the source and bytecode inventory, bytecode magic number, inferred filename tag, source-less bytecode candidates, and static dynamic-loading indicators.  Collector and scanner outputs are CSV files so dataset construction can be audited and rerun.  Ambiguous cases remain in the raw scan results rather than being normalized away.

\subsection{Phase 1: Bytecode Exposure and Transparency}\label{sec:method:extract}

The first phase turns collected artifacts into bytecode-exposure and transparency measurements.  It is a static archive-inspection phase: the scanner opens wheels, source distributions, zip archives, tar archives, individual files, and extracted directories without installing or executing package code, then records the fields summarized in Table~\ref{tab:phase1-scan-fields}.

\begin{table}[htp]
  \centering
  \caption{Phase~1 scan fields and purpose.}
  \label{tab:phase1-scan-fields}
  \begin{tabular}{p{0.30\linewidth}p{0.52\linewidth}}
    \toprule
    Field & Purpose \\
    \midrule
    Artifact type & Separate wheels, source distributions, and other archives. \\
    Source files & Measure whether bytecode is accompanied by visible Python source. \\
    \texttt{.pyc} files / pycache directories & Measure bytecode exposure at artifact and file levels. \\
    Source-less candidates & Approximate bytecode that lacks a plausible source counterpart in the same artifact. \\

    \bottomrule
  \end{tabular}

These fields separate prevalence from transparency.  Prevalence is measured at both artifact level and file level because one artifact with many cached files differs from many artifacts each containing one bytecode file.  Transparency is measured by whether a \texttt{.pyc} file has a plausible corresponding source file under package layout and pycache naming conventions.  This is a conservative visibility check, not a semantic-equivalence claim.
%
The scanner preserves ambiguous observations in the raw results.  Unknown bytecode versions, noncanonical filename tags, source-less candidates, and dynamic-loading indicators remain visible in the scan inventory; later phases decide which observations are suitable for version-matched analysis.  This keeps the prevalence measurement descriptive while preventing later tool failures from being mixed with raw ecosystem inventory.

\subsection{Phase 2: Practical Analyzability}\label{sec:method:source}

The second phase measures whether observed bytecode is practically analyzable by selected tools.  We distinguish loading, disassembly, partial decompilation, and full decompilation because each level supports a different security workflow.  RQ2 operates at the \texttt{.pyc}-file level.  For each bytecode-containing artifact, {\tech} extracts every \texttt{.pyc} entry, resolves its CPython tag, and includes it in RQ2 only when the tag is a supported modern CPython version with a prepared matching interpreter.  In the current study scope, this means CPython~3.8 and later; CPython~3.7 and earlier, PyPy tags, unknown tags, and noncanonical tags without an interpreter mapping are retained in the raw scan inventory but excluded from RQ2.  This filter is applied during tool analysis rather than during scanning, so the raw prevalence measurement remains complete while RQ2 failure counts are not polluted by out-of-scope runtime requirements.

The environment-preparation step reads the version summary produced by the scanner, uses the interpreter field to identify canonical CPython runtimes, locates matching interpreters, and automatically prepares missing analysis environments when the host supports installation.  Per-version virtual environments install tools that are sensitive to CPython bytecode format, while tools that are version-independent are treated as global tools.

The practical analyzability levels are: not loadable, loadable only, disassemblable, partially decompilable, and fully decompilable by the selected tools.  {\tech} records the status and failure reason for each analysis step, including marshal failure, disassembly failure, unsupported bytecode version, external-tool timeout, nonzero tool exit, and decompiler output that is unavailable.  Missing interpreters are recorded during environment preparation; after the RQ2 scope filter, they are not counted as tool failures.  This phase answers RQ2 by separating artifact-level analyzability from environment artifacts such as running a Python~3.12 bytecode sample under a Python~3.10-only setup.

This version-aware design is necessary because Python bytecode is version-sensitive: a tool failure is uninterpretable unless the analysis environment matches the bytecode version.  The version-aware setup therefore prevents false negatives caused by missing interpreters.  The selected-tool framing also prevents overclaiming: RQ2 reports what current selected tools can analyze, not what is theoretically analyzable.

\paragraph{Tool selection.}
We select bytecode-analysis tools using five criteria.  \textbf{C1: Availability} requires the tool to be publicly available and runnable locally, so experiments do not depend on closed services.  \textbf{C2: Python~3 support} requires support for at least one modern Python~3 bytecode format relevant to our dataset.  \textbf{C3: Practical adoption} requires evidence of use, such as packaging, documentation, references by reverse engineers, or use by Python developers.  \textbf{C4: Maintenance or stability} requires the tool to be actively maintained or stable enough to serve as a reproducible baseline.  \textbf{C5: Method diversity} requires the selected set to cover distinct analysis modes: parsing/loading, disassembly, and source-level decompilation.

We do not claim this set exhausts all Python bytecode tooling.  Instead, it covers the main practical analysis levels available to users: loading, disassembly, and source-level decompilation.  The set combines CPython reference functionality, established decompilers, an independent implementation, and a recent decompiler with broad Python~3 support.

\subsection{Phase 3: CPython Bytecode Fuzzing}\label{sec:method:recovery}

The third phase tests CPython robustness when processing malformed or adversarial bytecode artifacts.  {\tech} fuzzes CPython bytecode processing by version.  For a command such as \texttt{pybcSEC --fuzzing 3.10}, the tool resolves the requested CPython tag, prepares or reuses a matching interpreter, extracts source seeds from CPython's unittest suite, compiles those seeds into version-matched \texttt{.pyc} files, and runs honggfuzz against a small non-importing bytecode harness.  If raw unittest seeds or CPython source are missing, {\tech} downloads the matching CPython source release, extracts the unittest seeds, and compiles them locally.  Reruns reuse compiled seeds to keep the workflow reproducible and efficient.

The harness processes bytecode without importing package modules by name.  It attempts bytecode loading, raw code-object unmarshalling when appropriate, disassembly, and code-object serialization, but it does not execute arbitrary package behavior as application code.  Outcomes are classified as normal processing, Python-level exception, timeout, crash, abort, or other abnormal termination.  Crash counts are treated as robustness findings requiring triage, not automatically as security vulnerabilities.

This design follows from the security model behind RQ3.  Bytecode observed in benign packages is typically treated as trusted, but malware or tampering can supply bytecode that is malformed or adversarial.  CPython unittest-derived seeds give honggfuzz valid, version-matched starting points that cover real language features, while bytecode mutation explores states outside the ordinary compiler path.  The non-importing harness limits accidental package execution and focuses the measurement on interpreter bytecode processing.

\subsection{Phase 4: Source-Reproduction Analysis}\label{sec:method:runtime}

RQ4 checks how far selected source-level workflows can explain bytecode-level findings from RQ3.  For each honggfuzz finding, {\tech} reruns the bytecode under the same version-specific harness, invokes selected decompilers, compiles any emitted source with the matching interpreter, and reruns the compiled \texttt{.pyc}.  A finding is counted as source-reproduced only when the source-derived bytecode reaches the same behavior class as the original finding.

The result is tool-bounded.  If selected decompilers fail to emit source, emit uncompilable source, or emit source that does not reproduce the behavior, {\tech} reports \emph{not reproduced by selected tools}.  This does not prove that no source-level reproducer exists.  It shows that the selected source-recovery workflow did not produce one, which is the claim needed to interpret RQ3 without overstating bytecode-only behavior.

This check is needed because bytecode fuzzing can produce inputs that ordinary Python source may never generate.  Without RQ4, crash results would be easy to misinterpret as source-level interpreter vulnerabilities.  The decompile--compile--rerun workflow is a practical test of whether existing source-recovery tools can bridge the gap for a finding; its negative result is therefore explicitly limited to those tools.

\subsection{Tool Support and Evaluation Mapping}\label{sec:method:tools}

{\tech} is implemented as a modular Python package.  The collector, scanner, RQ2 tool analyzer, RQ3 fuzzing driver, and RQ4 source-reproduction driver are separate components with CSV outputs at each stage.  This design keeps the workflow simple for full-study runs while preserving intermediate artifacts for auditing and reruns.  It also keeps measurement responsibilities separate: the scanner records what exists in distributions, whereas RQ-specific analyzers decide which observations are in scope for a particular research question.

The version-management logic is central to the design.  The scanner exports a CPython-version summary, and later phases use that list to prepare matching interpreters and per-version environments.  RQ2 uses the scanner's interpreter mapping to select modern CPython bytecode entries with prepared runtimes and excludes older or unsupported entries from tool-failure counts.  This avoids the misleading failure mode where a bytecode artifact is judged unanalyzable only because the host machine lacks the correct CPython version.

The fuzzing component is also version-aware.  It extracts CPython unittest seeds, compiles them using the same interpreter version that will be fuzzed, and stores one seed corpus per CPython tag.  The source-reproduction component consumes RQ3 findings and reports decompiler, compilation, and reproduction outcomes separately so that evaluation claims remain tied to observable tool behavior.

\subsection{Ethical and Safety Considerations}\label{sec:method:ethics}

The study does not execute unknown packages on the host system.  Package installation, import probing, decompilation, and runtime tests are performed in isolated environments with network access disabled unless a dataset-construction step explicitly requires downloading public artifacts.  Malicious or suspicious samples are handled as research data, and bytecode-only crashes are reported as robustness findings rather than automatically being labeled exploitable vulnerabilities.  When a finding indicates a potential interpreter security issue, it should be disclosed through the appropriate upstream security process before public release.
