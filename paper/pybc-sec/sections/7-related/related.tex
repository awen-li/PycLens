\section{Related Work} \label{sec:related}

\subsection{Python Package and Supply-Chain Security}

Prior work and operational tools for Python package security focus on malicious packages, dependency risks, install-time behavior, typosquatting, dependency confusion, and ecosystem-scale measurement.  These efforts are essential, but they typically prioritize source files, package metadata, dependency graphs, and runtime behavior.  {\tech} complements this line of work by treating compiled Python artifacts as first-class objects whose source visibility must be measured rather than assumed.

\subsection{Python Decompilation and Bytecode Analysis}

Python decompilers such as \texttt{pycdc}~\cite{pycdc} attempt to reconstruct source from code objects.  They are valuable for reverse engineering and malware triage, but they face version compatibility, unsupported opcode, control-flow reconstruction, and metadata-consistency challenges.  This paper does not propose a new decompiler.  Instead, it evaluates whether decompilation and recompilation are sufficient for security workflows that want to reduce bytecode artifacts back to source-level analysis.

\subsection{Runtime Testing and Fuzzing}

Fuzzing and runtime testing have exposed many classes of implementation bugs~\cite{manes2018fuzzing,li2023pyrtfuzz}.  Python runtime fuzzing has studied interpreter behavior from source-level and runtime-level inputs, while byte-level fuzzing can expose parser and loader failures.  {\tech} differs by combining bytecode-level testing with tool-bounded source-reproduction analysis, allowing robustness findings to be interpreted in terms of whether selected source-recovery workflows can reproduce them.

\subsection{Program Analysis Beyond Source}

Security analysis often needs representations beyond source, including intermediate representations, binary code, dynamic traces, and cross-language behavior.  The same lesson applies to Python bytecode: a source representation is useful but not always complete.  A package may expose only a source-level loader while the behavior of interest resides in a marshalled code object, a source-less module, or a bytecode artifact that targets a different CPython version.  {\tech} focuses on this gap between source-visible Python and executable Python code objects in real package distributions and interpreter inputs.
