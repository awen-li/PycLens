\section{Introduction}\label{sec:intro}

Python is a major substrate for modern software, data processing, automation, scientific computing, cloud services, and developer tooling.  Its package ecosystem also makes Python an attractive target for supply-chain abuse: malicious packages, typosquatting, dependency confusion, install-time payloads, and obfuscated code can all place attacker-controlled behavior into otherwise routine development workflows.  As a result, a large body of security tooling has grown around Python package inspection, dependency analysis, malware triage, and program analysis.

Most of this tooling is source-centric.  It inspects \texttt{.py} files, package metadata, dependency declarations, build scripts, and installation behavior.  This focus is natural because Python source is readable, portable, and easy to parse.  It is also incomplete.  CPython does not execute source text directly; it compiles source into code objects whose instruction streams are Python bytecode.  These code objects are routinely cached as \texttt{.pyc} files and may also appear in source-less modules, deployment artifacts, custom import loaders, application bundles, and marshalled payloads.  In these settings, the executable representation available to the interpreter may differ from the source representation available to a scanner.

The difference matters for security.  A package may contain bytecode without corresponding source, bytecode whose contents no longer match nearby source, or dynamically loaded marshalled code objects that evade source-only inventory.  A malware analyst may try to recover source from compiled payloads, but decompilation is version-sensitive and incomplete for unusual control flow, unsupported opcodes, inconsistent metadata, or malformed code objects.  A runtime tester may mutate bytecode and expose interpreter failures, but raw mutation often produces malformed inputs whose security relevance is unclear.  These issues point to a broader question: how much of Python's bytecode risk surface is visible through source-level workflows, and where do current tools lose coverage?

This paper studies Python bytecode as a security-relevant artifact.  We do not claim that arbitrary untrusted bytecode should be safe to execute, nor do we equate every bytecode-level crash with an exploitable vulnerability.  Instead, we ask whether bytecode artifacts that arise in realistic workflows are visible to existing analysis, whether source recovery works well enough to support source-level security tooling, and whether CPython fails gracefully at the boundary where bytecode artifacts are parsed, loaded, and executed.

We make the following contributions:
\begin{itemize}[leftmargin=1.25em]
  \item We design a package-scale methodology for identifying Python bytecode artifacts, including \texttt{.pyc} files, source-less modules, bundled bytecode, marshalled code objects, and dynamic loading patterns.
  \item We characterize source/bytecode correspondence by checking whether bytecode has matching source, mismatched source, no source, or only dynamically generated/loadable origins.
  \item We evaluate bytecode recovery workflows through decompilation, recompilation, equivalence checks, and scanner visibility tests, exposing where source-level tooling loses behavior.
  \item We study CPython runtime robustness on real and generated bytecode inputs across multiple interpreter versions, classifying outcomes by parsing, metadata, control-flow, and execution failures.
  \item We introduce source-reachability analysis for bytecode-level findings, separating behaviors that can be reproduced from ordinary Python source from behaviors that remain bytecode-only under current tools.
\end{itemize}

The central result is a visibility gap rather than a single tool bug: Python bytecode is not merely an internal cache format, and security workflows that ignore it can miss executable behavior.  This motivation directly shapes our design.  Because the problem is not only whether bytecode exists but whether it is visible, recoverable, and source-reachable, {\tech} measures each step explicitly: artifact prevalence, source correspondence, tool recovery, runtime behavior, and source reachability.  The evaluation is organized around the same chain so that every design decision is tied to an empirical question rather than presented as an isolated engineering choice.
