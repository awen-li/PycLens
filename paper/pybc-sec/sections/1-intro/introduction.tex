\section{Introduction}\label{sec:intro}

Python is a major substrate for modern software, data processing, automation, scientific computing, cloud services, and developer tooling.  Its package ecosystem also makes Python an attractive target for supply-chain abuse: malicious packages, typosquatting, dependency confusion, install-time payloads, and obfuscated code can all place attacker-controlled behavior into otherwise routine development workflows.  As a result, a large body of security tooling has grown around Python package inspection, dependency analysis, malware triage, and program analysis.

Most of this tooling is source-centric.  It inspects \texttt{.py} files, package metadata, dependency declarations, build scripts, and installation behavior.  This focus is natural because Python source is readable, portable, and easy to parse.  It is also incomplete.  CPython does not execute source text directly; it compiles source into code objects whose instruction streams are Python bytecode.  These code objects are routinely cached as \texttt{.pyc} files and may also appear in source-less modules, deployment artifacts, custom import loaders, application bundles, and marshalled payloads.  In these settings, the executable representation available to the interpreter may differ from the source representation available to a scanner.

The difference matters for security.  A package may contain bytecode without corresponding source, bytecode whose contents no longer match nearby source, or dynamically loaded marshalled code objects that evade source-only inventory.  A malware analyst may try to recover source from compiled payloads, but decompilation is version-sensitive and incomplete for unusual control flow, unsupported opcodes, inconsistent metadata, or malformed code objects.  A runtime tester may mutate bytecode and expose interpreter failures, but raw mutation often produces malformed inputs whose security relevance is unclear.  These issues point to a broader question: how much of Python's bytecode risk surface is visible through source-level workflows, and where do current tools lose coverage?

This paper studies Python bytecode as a security-relevant artifact.  We do not claim that arbitrary untrusted bytecode should be safe to execute, nor do we equate every bytecode-level crash with an exploitable vulnerability.  Instead, we ask whether bytecode artifacts in PyPI distributions are visible to source-level inspection, whether selected tools can analyze them in a version-aware environment, whether CPython fails gracefully when bytecode is malformed or adversarial, and whether selected source-recovery tools can reproduce bytecode-level findings from ordinary source.

We make the following contributions:
\begin{itemize}[leftmargin=1.25em]
  \item We design a package-scale methodology for measuring bytecode prevalence and transparency in PyPI artifacts, including \texttt{.pyc} files, pycache directories, source-less bytecode candidates, bytecode versions, and dynamic loading patterns.
  \item We evaluate practical bytecode analyzability with selected tools in version-aware CPython environments, separating artifact limitations from missing-interpreter and tool-compatibility failures.
  \item We study CPython robustness under bytecode fuzzing by extracting CPython unittest-derived seeds, compiling version-matched \texttt{.pyc} corpora, and classifying abnormal bytecode-processing outcomes.
  \item We introduce tool-bounded source-reproduction analysis for bytecode-level findings, distinguishing findings reproduced by selected source-recovery workflows from findings those tools do not reproduce.
\end{itemize}

The central result is a visibility and interpretation gap rather than a single tool bug: Python bytecode is not merely an internal cache format, and security workflows that ignore it can miss executable artifacts or misinterpret bytecode-level failures.  This motivation directly shapes our design.  {\tech} measures each step explicitly: package prevalence and transparency, practical analyzability, runtime robustness, and tool-bounded source reproduction.  The evaluation is organized around the same chain so that every design decision is tied to an empirical question rather than presented as an isolated engineering choice.
