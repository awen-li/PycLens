
\section{Study Methodology}\label{sec:tech}

{\tech} is an empirical pipeline for studying Python bytecode visibility and robustness.  It has four goals.  First, it must find bytecode artifacts in realistic software distributions rather than only in synthetic benchmarks.  Second, it must relate bytecode back to source when possible, because most existing security tools operate at the source level.  Third, it must evaluate recovery tools without assuming that decompiled source is semantically equivalent to the original bytecode.  Fourth, it must classify runtime failures carefully so that malformed-input crashes, interpreter robustness issues, and source-reachable behaviors are not conflated.

\subsection{Framework Overview}\label{ss:overview}

The pipeline consists of five stages.  The dataset builder collects packages and application artifacts.  The extractor inventories source files, \texttt{.pyc} files, \texttt{\_\_pycache\_\_} directories, marshalled code objects, bytecode-bearing archives, and dynamic loading patterns.  The correspondence analyzer compiles available source under the expected interpreter version and compares it with observed bytecode.  The recovery analyzer applies decompilation and recompilation workflows, then compares recovered artifacts against the original bytecode.  Finally, the robustness analyzer runs real and generated bytecode inputs across CPython versions and applies source-reachability checks to abnormal outcomes.

\subsection{Design Rationale and Soundness Scope}\label{sec:method:soundness}

{\tech} is designed around a conservative notion of evidence.  It does not infer that bytecode is malicious, vulnerable, or source-less merely because a tool fails.  Instead, each stage records what was observed and what assumption was needed to make the next comparison.  This distinction addresses three soundness risks.

First, input soundness depends on dataset provenance and parsing correctness.  We therefore record distribution type, package version, artifact hash, bytecode magic number, and interpreter version.  Inputs that cannot be parsed, whose Python version cannot be inferred, or whose loader behavior is ambiguous are classified separately rather than forced into matching or mismatching categories.

Second, correspondence soundness depends on comparing bytecode under a compatible compiler.  Python bytecode changes across versions, so {\tech} compiles candidate source with the inferred interpreter version whenever possible and reports version mismatch as an explicit outcome.  Exact bytecode equality is used when available; relaxed structural comparison is used only to explain differences such as line metadata or position tables.

Third, recovery and robustness soundness depend on interpretation.  A decompiler failure indicates a recovery limitation, not proof that source never existed.  A crash on mutated bytecode indicates a robustness finding, not automatically an exploitable vulnerability.  Source-reachability analysis is included precisely to determine whether a bytecode-level behavior can be reproduced through ordinary source-level workflows.
