
\section{Study Goals and Research Questions}\label{sec:study}

This study asks whether Python bytecode should be treated as a first-class security artifact rather than as an incidental cache file.  The question has a causal structure.  Bytecode first needs to be visible in real distributions; otherwise, later analysis would lack practical relevance.  If it is visible, the next concern is whether existing tools can inspect it under the correct runtime assumptions.  If tool support is limited, robustness testing must distinguish bytecode-level interpreter behavior from source-level behavior.  Finally, any bytecode-level finding must be interpreted with care: failure to recover a source reproducer is evidence about selected tools, not proof that no source-level reproducer exists.

The study distinguishes benign distribution artifacts from adversarial bytecode inputs.  In ordinary packaging workflows, bytecode may appear as a build byproduct, cache file, or bundled artifact.  Such bytecode is usually treated as part of a trusted package once the package is selected for installation or analysis.  The adversarial setting considered in this study is different: an attacker may publish, replace, or tamper with bytecode so that CPython receives inputs that were not produced by the normal source compiler path.
%
We therefore evaluate two complementary risks.  First, bytecode in public distributions may reduce transparency when source is missing or does not obviously correspond to the bytecode.  Second, malformed bytecode may exercise interpreter paths that ordinary Python source does not reach.  The study does not assume that every observed \texttt{.pyc} file is malicious, and robustness findings are not automatically treated as exploitable vulnerabilities.  This threat model explains why prevalence, analyzability, robustness, and source reproduction are measured as separate properties.

We therefore organize the study around four goals.  G1 measures real-world exposure and source transparency in package distributions.  G2 measures practical analyzability with selected bytecode tools in version-aware environments.  G3 measures CPython robustness when processing malformed or adversarial bytecode.  G4 bounds the source-level interpretation of bytecode findings by testing whether selected recovery workflows can reproduce them from ordinary source.  These goals intentionally separate prevalence, tool support, runtime behavior, and source reproduction so that each claim has a clear input, metric, and limitation.

\begin{description}[style=unboxed,leftmargin=0cm]
\denseitems
\item[\textbf{RQ1 (G1):}] \emph{How prevalent and transparent are bytecode artifacts in Python distributions?}
\item[\textbf{RQ2 (G2):}] \emph{How practically analyzable are Python bytecode artifacts with existing tools?}
\item[\textbf{RQ3 (G3):}] \emph{How robust is CPython when processing malformed or adversarial bytecode artifacts?}
\item[\textbf{RQ4 (G4):}] \emph{Can bytecode-level failures be reproduced from ordinary source using selected tools?}
\end{description}

The ordering is part of the study design.  RQ1 establishes whether bytecode artifacts occur at ecosystem scale and whether source-level inspection is sufficient.  RQ2 evaluates the practical analysis boundary for the observed modern CPython bytecode subset.  RQ3 then moves from observed benign artifacts to adversarial bytecode inputs to test interpreter robustness.  RQ4 prevents overinterpretation of RQ3 by asking whether selected source-recovery workflows can bridge bytecode findings back to ordinary source.  


\section{Methodology}\label{sec:method}

\subsection{Overview}\label{sec:method:overview}

This study treats Python bytecode as a distribution artifact, an analysis target, and an interpreter input.  As shown in Figure~\ref{fig:pipeline-overview}, the study proceeds from ecosystem measurement to tool analysis, runtime robustness testing, and source-reproduction checking.  RQ1 measures bytecode exposure and source transparency in PyPI distributions; RQ2 evaluates the practical analyzability of the observed modern CPython bytecode subset; RQ3 tests CPython robustness under mutated bytecode inputs; and RQ4 checks whether bytecode-level findings can be reproduced from ordinary source using selected tools.
%
The pipeline has four stages aligned with these questions.  First, the data collector downloads Python package artifacts from PyPI and the scanner inventories source files, \texttt{.pyc} files, pycache directories, bytecode versions, source-less bytecode candidates, and dynamic loading patterns.  Second, the tool-analysis stage evaluates whether selected bytecode tools can load, disassemble, and decompile the modern CPython bytecode subset for which version-matched interpreters are prepared.  Third, the CPython fuzzing stage extracts unittest-derived seeds, compiles them into version-matched \texttt{.pyc} files, and fuzzes CPython bytecode processing with honggfuzz.  Fourth, the source-reproduction stage checks whether bytecode-level findings can be reproduced from ordinary source using selected recovery tools.

\subsection{Data Collection}\label{sec:method:data}

The data-collection component defines the study population for prevalence measurement and the package-derived inputs for later analysis.  We use PyPI because prior empirical and security studies treat it as the central Python package ecosystem for studying package vulnerabilities, dependency risk, and malicious-package detection~\cite{duan2021measuring,alfadel2023empirical,gao2025malguard}.  This is sufficient for our goal: RQ1 asks how bytecode appears in real-world Python distributions, and PyPI provides the public distribution artifacts consumed by package installers and package-security workflows.  PyPI also exposes distribution files through documented index and metadata APIs, which makes the population reproducible~\cite{pypi-index-api,pypi-json-api}.  The boundary is therefore wheels and source distributions, the standard package distribution formats described by Python packaging documentation~\cite{python-packaging-flow,python-package-formats}.  Installed environments, containers, application bundles, and repository snapshots are downstream or development contexts with different denominators, so we keep them outside the prevalence population.

Table~\ref{tab:data-collection-design} summarizes the collection choices that define the dataset denominator.

\begin{table}[htp]
  \centering
  \caption{Data-collection choices and purpose.}
  \label{tab:data-collection-design}
  \begin{tabular}{p{0.24\linewidth}p{0.58\linewidth}}
    \toprule
    Choice & Purpose \\
    \midrule
    PyPI artifacts & Official public Python package distribution population with a documented index and clear denominator~\cite{pypi-docs,pypi-index-api}. \\
    Latest release & Uses PyPI release metadata~\cite{pypi-json-api} to select the package version most likely encountered by users and package-security tools. \\
    One wheel and one source distribution & Covers the standard distribution formats~\cite{python-package-formats} while preventing projects with many platform-specific wheels from dominating prevalence counts. \\
    Five-year upload window & Focuses on contemporary packaging practice and modern CPython/tool support. \\
    CSV manifests & Keeps collection auditable, rerunnable, and easy to aggregate. \\
    \bottomrule
  \end{tabular}
\end{table}

The collector enumerates package names from the PyPI simple index, queries PyPI's JSON metadata, and selects artifacts from each package's latest release.  For each selected release, it keeps at most one wheel and one source distribution uploaded within the five-year study window.  If the latest release has no selected wheel or source distribution within the window, the package contributes no artifact to the collected dataset.  Source distributions may appear as \texttt{.tar.gz}, \texttt{.zip}, or related archive formats; the scanner records the concrete artifact type.
%
The collection policy shapes the denominator.  Because the dataset is package-balanced rather than upload-balanced, projects with many platform-specific wheels do not dominate the measurement.  We therefore analyze wheels and source distributions as separate strata and report the combined total only as a descriptive summary.
%
For each downloaded artifact, the collector records the package name, version, distribution type, local path, hash, and collection status.  Downloads are parallelized, resumable, and stored under a deterministic layout keyed by source, package, version, and filename.  The scanner then records the source and bytecode inventory, bytecode magic number, inferred filename tag, source-less bytecode candidates, and static dynamic-loading indicators.  Collector and scanner outputs are CSV files so dataset construction can be audited and rerun.  Ambiguous cases remain in the raw scan results rather than being normalized away.
