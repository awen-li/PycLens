\subsection{Phase 3: Interpreter Robustness Under Adversarial Bytecode}\label{sec:method:recovery}

The third phase measures how CPython behaves when bytecode inputs are malformed or adversarial.  The unit is a version-matched \texttt{.pyc} file, and the measured property is robustness of bytecode processing: a malformed input should be rejected by ordinary Python-level failure modes rather than causing an interpreter crash, abort, or uncontrolled hang.
%
Figure~\ref{fig:rq3-fuzzing-workflow} summarizes the version-aware workflow.  The input is the set of modern CPython versions observed in Phase~1 for which a matching interpreter can be prepared; unsupported legacy or non-CPython versions are recorded as out of scope for this phase.  For each version, the phase prepares or reuses the matching interpreter, extracts source seeds from CPython's unittest suite, compiles those seeds into a version-matched \texttt{.pyc} corpus, and feeds the corpus to the \texttt{honggfuzz} backend~\cite{honggfuzz}.  The backend records the execution outcome for each version-specific run.  If the unittest sources are not available locally, the matching CPython source release is obtained and used only for seed extraction.  Compiled seed corpora are stored per CPython version so repeated runs use the same starting population.

The workflow in Figure~\ref{fig:rq3-fuzzing-workflow} separates three concerns that make the measurement interpretable.  First, version matching attributes failures to bytecode processing rather than interpreter mismatch.  Second, unittest-derived seeds start from valid bytecode generated from CPython's own regression tests, which exercise core language and runtime functionality.  This seed quality is important for mutation-based fuzzing: a richer initial corpus reaches more meaningful interpreter behavior before mutation explores malformed states outside the source-compiler path.  Third, the fuzzing harness loads each mutated \texttt{.pyc} file and runs the embedded bytecode with the matching CPython interpreter.  Each run is bounded by timeout and process isolation, and the harness records the resulting behavior as normal execution, Python-level exception, timeout, crash, abort, or other abnormal termination.  We treat crashes, aborts, and persistent timeouts as abnormal findings for RQ3.  Such findings require triage and are not automatically classified as exploitable security vulnerabilities.

\subsection{Phase 4: Source-Reproduction Analysis}\label{sec:method:runtime}

The fourth phase bounds the source-level interpretation of bytecode-level findings from RQ3.  The unit is an abnormal RQ3 finding, such as a crash, abort, or persistent timeout.  For each finding, the phase first reruns the original mutated \texttt{.pyc} under the same version-specific harness to confirm the observed behavior.  It then invokes the selected decompilers from Phase~2, compiles any emitted source with the matching CPython interpreter, and reruns the resulting \texttt{.pyc} under the same harness.  A finding is counted as source-reproduced only when this source-derived bytecode reaches the same behavior class as the original finding.

This design separates three outcomes that otherwise collapse together.  A decompiler may fail to emit source, the emitted source may fail to compile, or the recompiled source may execute but not reproduce the original behavior.  All three cases are reported as \emph{not reproduced by selected tools}, with the failure stage recorded separately.  The claim is therefore tool-bounded: it does not prove that no source-level reproducer exists, only that the selected recovery workflow did not produce one.

This check is needed because bytecode mutation can create code-object states that ordinary Python source may not generate.  Without RQ4, an RQ3 crash could be misread as a source-level interpreter failure.  The decompile--compile--rerun workflow tests whether selected source-recovery tools can bridge that gap for each finding, while keeping negative results limited to the evaluated tools.
