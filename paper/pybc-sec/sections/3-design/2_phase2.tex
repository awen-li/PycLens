\subsection{Source Correspondence and Recovery Analysis}\label{sec:method:source}

For each bytecode artifact, {\tech} searches for corresponding source using path conventions, module names, archive metadata, and package layout.  When source is available, the pipeline compiles it under the expected Python version and compares the resulting code object against the observed bytecode.  The comparison includes opcode sequences, constants, names, locals, nested code objects, control-flow shape, exception tables, flags, and line metadata.  We classify artifacts as source-present and matching, source-present but mismatched, source-missing, dynamically generated or loaded, bundled or packed, or unknown.

{\tech} then evaluates source recovery.  It runs selected decompilers on bytecode artifacts, checks whether recovered source is syntactically valid, recompiles the recovered source, and compares the resulting bytecode and behavior with the original when execution is safe and deterministic.  Failure categories include unsupported Python versions, unsupported opcodes, unusual control flow, exception-table mismatch, malformed code-object metadata, dynamic loading, and cases where decompilation succeeds but recompilation changes behavior.  This distinction is important: decompilation failure does not prove that no source exists, but it does show that current recovery tools failed to produce a usable source-level representation.

The justification for this stage is that source visibility cannot be answered by file presence alone.  A \texttt{.py} file may exist but compile to different bytecode, while a decompiler may produce source that parses but no longer preserves the original behavior.  The evaluation therefore measures correspondence, recompilability, and equivalence separately.
