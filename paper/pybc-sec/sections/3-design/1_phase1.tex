\subsection{Phase 1: Bytecode Exposure and Transparency}\label{sec:method:extract}

The first phase turns collected artifacts into bytecode-exposure and transparency measurements.  It is a static archive-inspection phase: the scanner opens wheels, source distributions, zip archives, tar archives, individual files, and extracted directories without installing or executing package code.  Table~\ref{tab:phase1-scan-fields} summarizes the fields recorded by this scan.

\begin{table}[htp]
  \centering
  \caption{Phase~1 scan fields and purpose.}
  \label{tab:phase1-scan-fields}
  \begin{tabular}{p{0.30\linewidth}p{0.52\linewidth}}
    \toprule
    Field & Purpose \\
    \midrule
    Artifact type & Separate wheels, source distributions, and other archives. \\
    Source files & Measure whether bytecode is accompanied by visible Python source. \\
    \texttt{.pyc} files / pycache directories & Measure bytecode exposure at artifact and file levels. \\
    Source-less candidates & Approximate bytecode that lacks a plausible source counterpart in the same artifact. \\
    Version evidence & Record magic numbers and filename tags for later version-aware analysis. \\
    Dynamic-loading indicators & Flag source that may load or construct bytecode at runtime. \\
    \bottomrule
  \end{tabular}
\end{table}

These fields separate prevalence from source visibility.  Prevalence is measured at both artifact level and file level because one artifact with many cached files differs from many artifacts each containing one bytecode file.  Source visibility is measured by whether a \texttt{.pyc} file has a plausible corresponding source file under package layout and pycache naming conventions.  This is a conservative artifact-local check: it does not claim semantic equivalence, and it does not rule out source existing elsewhere.
%
The scanner preserves ambiguous observations in the raw results.  Unknown bytecode versions, noncanonical filename tags, source-less candidates, and dynamic-loading indicators remain visible in the scan inventory; later phases decide which observations are suitable for version-matched analysis.  Dynamic-loading indicators are static flags for APIs that may load or construct code objects; they do not prove that a bytecode payload is executed or identify the runtime target.  This keeps the prevalence measurement descriptive while preventing later tool failures from being mixed with raw ecosystem inventory.
